Phase 2, Chunk 2.3: Update /api/attachments/:id Endpoint for Direct Serving (Images)
This document outlines the next step in integrating OpenAI image generation: modifying the backend API endpoint responsible for serving attachments to correctly handle and serve generated images for direct display in the frontend.
Goal: Ensure the /api/attachments/:id GET endpoint in server/routes.ts retrieves image attachments from the database, sets the correct content type, and serves the image data in a way that allows browsers to display it directly.
Context:
* The files to modify are server/routes.ts and potentially server/storage.ts.
* The application has an existing GET endpoint, likely /api/attachments/:id, to retrieve attachment data.
* Image attachments are stored in the database as base64 strings (as implemented in Chunk 1.3).
* Browsers need the correct Content-Type header (e.g., image/png) to display images directly.
* The Content-Disposition header needs to be set appropriately to prevent browsers from forcing a download for image files.
* Detailed logging is required to track the process.
Implementation Plan:
1. Open server/routes.ts: Access and open the server/routes.ts file.
2. Locate Attachment Endpoint: Find the GET route handler for /api/attachments/:id. This handler likely retrieves an attachment record from the database using the provided id.
3. Retrieve Attachment Data: Ensure the route handler correctly retrieves the attachment record from the database using storage.getAttachmentById(id).
4. Handle Image File Type:
   * After successfully retrieving the attachment, check its fileType property.
   * If fileType starts with "image/" (e.g., "image/png", "image/jpeg"), this is an image file.
5. Set Content Type Header:
   * For image files, set the Content-Type header of the response to the retrieved attachment.fileType.
   * For non-image files, retain the existing logic for setting the Content-Type (e.g., "text/csv" for CSV files).
6. Control Content Disposition:
   * For image files, adjust the Content-Disposition header. To allow direct display in the browser (e.g., within an <img> tag), the Content-Disposition should be set to "inline" or potentially omitted entirely. Review your existing code's handling of this header and modify it to differentiate between images and other file types. For non-image files, keep the Content-Disposition set to "attachment" to trigger a download.
7. Decode and Send Data:
   * Retrieve the base64 content from attachment.content.
   * Decode the base64 string into a buffer using Buffer.from(attachment.content, 'base64').
   * Send the buffer as the response body.
8. Implement Error Handling: Add robust error handling:
   * If the attachment ID is not found, return a 404 Not Found response.
   * If there's an error retrieving the attachment from storage or decoding the base64, log the error and return a 500 Internal Server Error response.
9. Add Detailed Logging: Add console.log statements:
   * At the start of the route handler, logging the requested attachment ID.
   * After retrieving the attachment, logging the filename and file type.
   * When setting the Content-Type and Content-Disposition headers for image files.
   * Before sending the response, logging the size of the data being sent.
   * In any catch blocks, logging the specific error.
Testing Plan:
1. Generate Test Image: Ensure you have at least one image attachment in your database generated by the AI (from testing previous chunks). Note its attachment ID.
2. Identify Endpoint: Confirm the exact URL structure for the attachment endpoint (e.g., GET /api/attachments/:id).
3. Test Direct Image Display: Open a web browser and navigate directly to the URL for your generated image attachment (e.g., http://localhost:3000/api/attachments/<your-image-attachment-id>).
   * Expected Outcome: The image should be displayed directly within the browser tab, not downloaded as a file. Check your browser's developer tools (Network tab) to confirm the Content-Type header is correct (e.g., image/png) and the Content-Disposition is suitable for inline display. Review server logs for corresponding messages.
4. Test Non-Image Download: If you have non-image attachments (like CSVs), test accessing their URLs in the browser.
   * Expected Outcome: The browser should prompt you to download the file. Check developer tools to confirm the Content-Type and Content-Disposition: attachment headers are correct.
5. Test Invalid ID: Attempt to access an attachment ID that does not exist.
   * Expected Outcome: The server should return a 404 Not Found response. Review server logs for the error handling message.
6. Verify Logging: Review server logs for all test runs to ensure the detailed logging messages accurately reflect the retrieval, processing, and serving of attachments.
